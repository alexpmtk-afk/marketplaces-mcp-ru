# Правила очереди запросов к WB и Ozon

Этот документ фиксирует только подтверждённые правила, по которым сервис
ограничивает запросы. Он не содержит ключей доступа, названий продавцов или
данных кабинетов.

## Wildberries

- Ограничения относятся к аккаунту продавца и к конкретному методу либо группе
  методов, а не к одному общему лимиту на весь WB.
- Для текущих персональных ключей Marketplace-категория допускает 300 запросов
  в минуту с равномерной паузой 200 миллисекунд и кратковременной серией до 20
  запросов. У отдельных методов могут быть более строгие правила.
- Сервис использует стабильный идентификатор продавца внутри ключа доступа,
  преобразованный в необратимый хеш. Поэтому замена ключа того же продавца не
  создаёт новую очередь.
- При ответе «слишком много запросов» учитываются указания WB о времени
  следующей попытки; пауза относится к затронутому методу, а не ко всем
  операциям продавца.

Источник: https://dev.wildberries.ru/en/docs/openapi/api-information

## Ozon Seller

- Общий предел относится к Client-Id продавца: 50 запросов в секунду для всех
  методов вместе. Более узкие ограничения отдельных методов продолжают
  действовать поверх него.
- Текущие read-only методы `ozon_product_info_list`, `ozon_prices_get` и
  `ozon_stocks_info` явно помечены как покрытые этим доказанным общим лимитом.
  Это не создаёт выдуманный per-method лимит: все три проходят через общий
  Client-Id bucket 50 RPS, а непроверенные каталожные методы остаются fail-closed.
- Изменение цены одного товара ограничено 10 изменениями в час. Для этого
  используется отдельная очередь на товар; его идентификатор не записывается
  открытым текстом.
- Замена Api-Key при том же Client-Id не создаёт новую очередь.
- Если точное правило для обычного каталожного метода не подтверждено, такой
  запрос не отправляется. Произвольные пути без каталога также не отправляются.

Источник: https://docs.ozon.ru/api/seller/

## Общие правила

- Повторные попытки и постраничная загрузка проходят через ту же очередь.
- Разные продавцы и разные маркетплейсы не блокируют друг друга без причины со
  стороны маркетплейса.
- В рабочем REMOTE общая очередь хранится в локальном Redis
  `127.0.0.1:6379`; наружу Redis не публикуется. `MARKETPLACE_REQUIRE_REDIS=1`
  обязателен; если Redis недоступен, запросы к маркетплейсам не отправляются.
- У WB нет общего transport-wide bucket. Любой старый `WB_GLOBAL_RPS` из
  Yandex-era окружения игнорируется, а legacy Redis-ключи `wb:*:global`
  удаляются при старте REMOTE.
- Production-проверка перед запуском/после миграции:
  `python scripts/check_rate_limit_backend.py --require-redis --repair-legacy-wb`.
