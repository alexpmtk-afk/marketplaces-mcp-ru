## Ключевые выводы

1. WB Orders — специализированный MCP должен уметь агрегировать диапазон дат и минимизировать upstream-вызовы. Для короткого диапазона допустим кандидат `flag=0` + фильтрация/группировка внутри backend при доказанной полноте ответа и корректной обработке pagination boundary.
2. Limiter нужно проектировать по фактическому scope ограничения API, а не просто по совпадению host/scope/rate-limit строки.
3. Старые/отключённые endpoint должны оставаться в историческом registry как provenance, но не должны быть доступны generic tool selection после lifecycle-блокировки.
4. Ozon требует срочного внимания к устаревшим posting/finance версиям; для production-миграции критичные замены должны быть сверены с актуальным официальным Swagger.

## Текущее состояние источников

- Прямое автоматическое чтение `dev.wildberries.ru` в текущем research-клиенте блокируется anti-bot/HTTP 498.
- Прямое автоматическое чтение `docs.ozon.ru/api/seller/` уходит в redirect loop.
- Поэтому официальный Swagger/OpenAPI остаётся высшим source of truth, но до его прямой выгрузки используются пинованные воспроизводимые вторичные snapshots + официальные change-notifications с явной маркировкой уровня доверия.

## Следующий gate

Перед любыми production-изменениями:

1. дождаться завершения текущей работы технического Codex по WB limiter/range;
2. получить новый canonical app SHA, если он изменится;
3. синхронизировать research branch с актуальным canonical HEAD;
4. пересобрать нормализованный `api_catalog.json`;
5. выполнить diff implementation catalog ↔ pinned OpenAPI snapshots;
6. только после этого готовить отдельные production changes для lifecycle blocking и missing replacements.

## Пользовательская выгрузка

Пока не требуется. Запрос пользователю нужен только если для конкретного критичного endpoint невозможно подтвердить контракт из доступных официальных источников. В таком случае запрашивается конкретный официальный Swagger/OpenAPI файл, без токенов и секретов.
